# &#x20;代码规范入口

本文是系统的**目标代码标准入口**，适用于新代码、被实质修改的代码和后续存量迁移。它不是现有代码写法的总结；存量实现或工具配置与本文冲突时，应记录为迁移差距，不能反向降低标准。

规范用词：**必须**表示强制要求；**应当**表示默认要求，偏离时需在代码评审中说明；**可以**表示允许选择。

## 1. 按任务加载

| 任务范围                               | 必读规范                                             |
| ---------------------------------- | ------------------------------------------------ |
| 任意代码或配置变更                          | 本文                                               |
| `service/` Java、Spring、API、日志      | [backend-code-style.md](backend-code-style.md)   |
| `ui/admin-ui/` 或 `ui/customer-ui/` | [frontend-code-style.md](frontend-code-style.md) |
| `service/sql/`、Mapper SQL、表结构      | [database-code-style.md](database-code-style.md) |

目录下的 `AGENTS.md` 只引用与当前任务有关的细则。不要为了“完整”而读取与任务无关的前端、后端或数据库规则。

## 2. 规范来源与优先级

规则按以下顺序解释：

1. 安全要求、数据保护要求和已批准的 OpenSpec 行为约束。
2. 本文及按任务加载的细则中明确写出的项目规则。
3. 各细则列出的权威外部基线。
4. 版本化的 formatter、lint 和类型检查配置。
5. 现有代码、模板代码和脚手架示例。

工具配置是规范可自动执行的实现；工具与规范冲突时，应修正工具或登记迁移计划。`AGENTS.md` 负责工作流程和目录边界，不重复维护具体细则。

## 3. 通用规则

### 3.1 文件与排版

- 所有文本文件必须使用 UTF-8、LF 换行并以一个换行符结尾。
- 禁止行尾空格、制表符缩进和无意义的连续空行。
- Java 使用 2 空格块缩进；JavaScript、Vue、CSS、SCSS、JSON、YAML 和 SQL 使用 2 空格缩进；仅使用 TypeScript 的项目同样使用 2 空格缩进；XML 使用 4 空格缩进。
- 一个文件应表达一个主要职责；文件名必须表达主要类型、组件或能力。
- 禁止提交编辑器临时文件、构建产物、运行日志、真实凭据和本机绝对路径。

### 3.2 命名与结构

- 名称必须表达业务含义，禁止缺少上下文的 `data`、`info`、`obj`、`temp`、`handle`、`process`。
- 包名已表达场景或访问范围时，类型名不得重复添加 `Public`、`Api` 等上下文前缀；类型名应采用“业务 + 动作 + 角色”，例如 `NewsQueryRequest`、`ToolSummaryResponse`。
- 布尔值使用可读谓词，如 `enabled`、`visible`、`hasPermission`、`canPublish`；集合和复数资源使用复数名。
- 时间名称必须带语义与单位，例如 `createdAt`、`expiresAt`、`timeoutSeconds`、`fileSizeBytes`。
- 函数和类应只有一个可概括职责；无法用一句话描述时应拆分。优先早返回降低嵌套。
- 消除重复业务规则，但不得为了“复用”建立跨领域的万能工具类。魔法值必须提升为有意义的常量、枚举或配置。
- 生成代码、第三方代码和 vendor 文件不得手工修改；应修改生成源或配置。

### 3.3 注释与文档

- 注释解释“为什么”“约束是什么”或“为什么没有采用显而易见的方案”，不复述代码。
- 对外接口方法必须说明用途、关键入参约束和返回/失败语义；DTO、请求和响应模型的属性在业务含义或取值约束不显然时必须注释；项目隔离、状态过滤、降级和安全处理等核心逻辑必须说明原因与边界。
- 不得为仅重复类名、方法名或属性名的内容添加类级或字段级注释；优先在真正承载约束的接口、属性或核心逻辑附近注释。
- 删除或修改代码时必须同步维护注释；`TODO` 必须包含可追踪事项或明确后续动作。
- 公共 API、非显然领域规则、重要边界条件和安全决策必须有文档。
- 代码标识符、命令和路径保留原始英文；解释性文档使用简体中文。

## 4. 自动化与质量门禁

| 工具                                    | 职责                                |
| ------------------------------------- | --------------------------------- |
| EditorConfig                          | 编码、换行和基础缩进                        |
| google-java-format / Spotless         | Java 确定性格式                        |
| Prettier                              | 前端与配置文件格式                         |
| ESLint                                | JavaScript、Vue 缺陷和语义规则         |
| TypeScript / vue-tsc / Nuxt typecheck | 使用 TypeScript 的项目的类型正确性     |
| OpenSpec validation                   | 变更工件结构和需求一致性                      |

- 被修改文件必须通过适用的 formatter check 与 lint；仅使用 TypeScript 的项目还必须通过 typecheck。构建验证和测试验证是不同门禁。
- `check` 不得隐式执行测试；是否执行测试必须由当前任务的明确授权决定。
- 自动修复后必须审查 diff。禁止通过全局关闭规则、宽泛 ignore，或在使用 TypeScript 的项目中降低严格度制造“通过”。

## 5. 例外与迁移

只有框架、第三方 API、兼容性或安全要求使规则无法合理执行时，才可偏离规范；例外必须缩小到最少文件或代码行、记录原因与移除条件，并经代码评审接受。

“现有代码一直这样写”“修改量大”“工具默认如此”不是永久例外理由，应转为迁移任务。新代码不得扩大已知差距；需要大规模机械修改时必须另立 OpenSpec change。

当前已知的 Java formatter profile 差距见 [backend-code-style.md](backend-code-style.md)。
